# Alloy Book 全面見直し設計（入門価値重視 + 実務導線）

## 背景

現行の `alloy-book` は Alloy の文法や操作導線はあるものの、以下が弱い。

- Alloy を設計で使うメリットが、読み始めの時点で腹落ちしない
- Analyzer/CLI の「使い方」は書かれているが「使う価値」が十分に接続されていない
- Analyzer 画面の実際の文言（例: `Execute`, `Show`）と本文の語が一致しない箇所があり、初学者が迷う

本設計は、Alloy 初学者がメリット理解を起点に学習を進められる構成へ再設計する。

## 目的

- 冒頭で「なぜ Alloy を使うのか」を理解できること
- 最小の操作で「設計判断に効く」体験を得られること
- 入門から実務導線（CLI/LSP/CI）に迷わず接続できること
- Analyzer の画面文言と本文文言を一致させ、手順の再現性を上げること

## 対象読者

二層構成で段階的にカバーする。

- 入門層: 形式手法や Alloy が初めての読者
- 実務導線層: 基礎は理解したが、チーム運用にどう繋げるかを知りたい読者

初版は入門層を厚くし、実務層は導線中心で最小限に留める。

## 非目標（初版ではやらないこと）

- CI 運用の複数比較パターンの提示
- LSP の詳細設定/拡張運用の深掘り
- 大規模ケーススタディの新規追加

## アプローチ比較

### 案1: 価値先行ストーリー型（採用）

- 冒頭で「設計課題 -> Alloy での改善」を提示
- 直後に最小ハンズオンで価値を体験
- その後で言語/操作の基礎へ進む

長所:

- 学習動機を維持しやすい
- 初学者の離脱を減らしやすい

短所:

- 冒頭章の設計と編集に工数がかかる

### 案2: 操作先行ハンズオン型

長所:

- すぐに手を動かせる

短所:

- 「なぜ使うか」が後置され、価値理解が遅れる

### 案3: 既存章維持の部分改修型

長所:

- 変更コストが低い

短所:

- 全面見直しの目的に対して効果が限定的

## 採用方針

案1（価値先行ストーリー型）を採用する。  
理由は、現課題が「手順不足」ではなく「価値伝達不足」にあるため。

## コンポーネント設計（章責務）

### `Why Alloy?`

- 設計での典型課題（曖昧さ、見落とし、主観議論）を示す
- 自然言語仕様と Alloy モデルの対比を 1 ページで示す

### `5分で価値を体験`

- 最小モデルをコピー実行
- `run` と `check` を 1 回ずつ試し、SAT/UNSAT を設計判断に翻訳

### `最初のモデル`

- `sig`/relation を「設計境界・関係表現」として説明
- `pred` を「問いの単位」として説明

### `言語の基礎`

- 制約/多重度/assert/check を用途中心で整理
- 理論詳細は一次情報へ誘導

### `Alloy Analyzer の操作`

- 操作手順ではなく「何が分かるか」を主語に再編
- 失敗時の最小デバッグ手順を明示

### `実務への接続ガイド`

- CLI/LSP/CI の価値を短く定義
- 最小導入シナリオを 1 本提示

### `次の一歩`

- 入門完了チェック
- 目的別ロードマップ（学習/研究/チーム導入）

## データフロー（編集運用フロー）

1. 章ドラフト作成
2. UI 文言監査（画面語との一致チェック）
3. スクリーンショット付き手順照合
4. 初学者視点レビュー
5. 公開前通しレビュー

## Analyzer 文言整合ポリシー

スクリーンショットで確認できる語彙（例: `New`, `Open`, `Reload`, `Save`, `Execute`, `Show`）を基準にする。

- 本文は画面ラベル優先で記述する
- 抽象語（例: run/check）だけで手順を記述しない
- 版差がある場合:
  - 本文: スクリーンショット基準語
  - 注記: 版差による代替語

補助資料として `analyzer-ui-glossary` を新設し、全章から参照する。

## エラーハンドリング設計（学習上の失敗対策）

- ボタン名が見つからない:
  - UI 語彙表と版差注記へ誘導
- SAT/UNSAT の意味が分からない:
  - 「設計判断への翻訳」ボックスで補助
- 手順どおりでも再現しない:
  - 章末に最小トラブルシュート（保存、スコープ、制約分割）を配置

## テスト設計（ドキュメント品質）

- 文言一致テスト:
  - 章中 UI 語と語彙表の一致確認
- 初心者理解テスト:
  - 各章で「なぜ使うか」を 1 文で言えるか
- 導線テスト:
  - 入門完了後の次アクションが明確か

## 実施順

1. 目次再編と章責務確定
2. 冒頭 2 章（価値 + 5分体験）を作成
3. 既存章を価値主語で改稿
4. Analyzer 文言を語彙表基準で一括整合
5. 実務導線章を追加
6. 通しレビュー

## 完了条件

- 初学者が 3 分以内に「Alloy を使う理由」を説明できる
- 手順記述が Analyzer 画面文言と矛盾しない
- 入門完了後の次アクションが明確に 1 つ提示されている

## リスクと軽減策

- リスク: 価値説明が抽象化しすぎる
  - 軽減策: 失敗例 -> Alloy での改善例のペアを各章に入れる
- リスク: 版差により文言が再度ずれる
  - 軽減策: UI 語彙表を単一ソース化し、更新手順を固定化
- リスク: 実務層が薄すぎる
  - 軽減策: 導線章で「次に読むべき一次情報」を明示
